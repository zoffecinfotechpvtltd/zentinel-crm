# Feature: Notifications

## Outcome

Everyone knows what needs their attention right now — an overdue follow-up, an invoice going unpaid, a Tally sync that's stalled — without having to remember to go check each screen individually. This replaces the prototype's `page-notifications` screen, which currently renders from a `notif-list` div that nothing in the file ever populates.

## Requirements

**In-app notifications** (build this first — it's the foundation everything else layers on):
- A `notifications` table, one row per (user, event). The nav bell badge count and the Notifications page both read from real unread rows — not the prototype's hardcoded `<span class="nav-badge">3</span>`.
- Notification types, each generated by the feature that owns the event (not centralized guessing):
  - `followup_due` / `followup_overdue` / `followup_escalated` — from Follow-up Automation
  - `invoice_overdue` — from Invoices' scheduled status job
  - `tally_sync_failed` / `tally_sync_stale` — from Payments & Tally Sync
  - `payment_unmatched` — from Payments & Tally Sync
  - `lead_assigned` / `project_assigned` — when someone is newly assigned something
- Each notification links to the relevant record (clicking it navigates straight to that lead/invoice/project) — the prototype's notification icons/text are static with no link target.
- Mark-as-read (individual and "mark all read" — the prototype has a "Mark all read" button already but nothing behind it).
- Notifications older than 30 days and already read are auto-archived (hidden from the default view, not deleted — soft-delete convention per architecture doc).

**Email digest (Phase 2, once in-app is solid):**
- A daily morning email per user summarizing their Today + Overdue follow-ups and any invoices/projects needing attention — this is what actually makes "someone should check the CMS" become "the CMS told me," rather than relying on people remembering to open the app.
- Not real-time email-per-event — a single daily digest avoids notification fatigue for a small team; only genuinely urgent items (Tally sync stalled, an invoice significantly overdue) warrant an immediate email outside the digest.

## Explicitly out of scope for v1

- Push notifications / native mobile app — this is a web tool used at desks; browser/email coverage is sufficient.
- WhatsApp/SMS notification delivery to staff — email + in-app is enough internally; WhatsApp is reserved for *client-facing* outreach (Follow-up Automation), not internal alerting.
- User-configurable notification preferences (granular on/off per type) — ship a sensible fixed set first; only add preferences if people actually complain about noise, which is unlikely at this volume.

## Data model

```sql
notifications(
  id, user_id references users(id) not null,
  type text not null, -- 'followup_overdue', 'invoice_overdue', etc.
  entity_type text, entity_id uuid, -- what it links to
  title text, body text,
  read_at timestamptz, archived_at timestamptz,
  created_at timestamptz default now()
)
```

## Acceptance criteria

- [ ] The nav bell badge count exactly matches the count of unread, non-archived notifications for the logged-in user — verified by seeding a known number and checking the badge, then marking one read and confirming the count decrements immediately.
- [ ] Clicking a notification navigates to the correct underlying record (a `followup_overdue` notification opens that specific lead; an `invoice_overdue` notification opens that specific invoice).
- [ ] "Mark all read" clears the badge and updates every visible notification's read state in one action, without a page reload.
- [ ] An invoice crossing into Overdue status (per the Invoices scheduled job) produces exactly one notification per relevant user (assigned Finance user + Admin), not one per user in the system.
- [ ] A stalled Tally sync (per Payments README's health check) produces a `tally_sync_stale` notification to all Finance + Admin users, and this is one of the "immediate" notifications, not held for the next day's digest.
- [ ] The daily digest email (Phase 2) contains only that recipient's own relevant items — verified with two users who have different overdue follow-ups and confirming no cross-contamination between their digests.
- [ ] Notifications older than 30 days and read are excluded from the default notifications view but still exist in the database (query directly to confirm soft-archive, not deletion).
